\chapter{Implementation}\label{ch:implementation}

After explaining the modifications to the Lock-Free Deduplication algorithm
in \Cref{ch:design} this chapter will provide a deeper insight into their
implementation in the form of the `Vinculum' library.
This library is implemented in the Rust~\cite{Rust} Programming Language, allowing
it to leverage its high-level features while having low-level control.

\section{Intended Usage}\label{sec:usage}

Vinculum is intended to assist authors of backup programs in implementing the
Lock-Free Deduplication algorithm while creating a fully functioning backup
program requires additional problems to be solved.
Before chunks can be uploaded to a repository they have to be created from the data
to be backed up, which itself is a problem with multiple existing solutions and tradeoffs
as shown by Duplicacy allowing to choose between two of them~\cite[section `Chunking']{Duplicacy}.
There are also additional use cases, such as compressing or encrypting the data
stored in the repository for additional space savings of protection from unwanted
access.

While Gilbert et al.~\cite{Duplicacy} provide solutions for them there are existing
alternatives such as the encryption used by Borg 2~\cite[section `Internals']{Borg2}
which itself is the result of further development of the encryption used in
Borg 1~\cite[section `Internals']{Borg1}.
Since this highlights the need for allowing alternative solutions to these
problems to be used with the Lock-Free Deduplication algorithm Vinculum is
designed to focus on the algorithm only and giving users the greatest possible
flexibility when implementing them.

\section{Structure}

With the primary goal being reusability Vinculum is structured as a `crate',
the concept representing libraries in the Rust ecosystem~\cite[section 20.4.]{Rust-Reference}.
Crates represent `unit[s] of compilation and linking'~\cite[section 20.4.]{Rust-Reference}
which can expose `Items'~\cite[section 20.4.]{Rust-Reference} consisting of
`Trait[s]' and `Struct[s]', among other things~\cite[section 6]{Rust-Reference}.
While a struct represents a type in the type system used by the Rust language
a trait represents an abstract interface that types can
implement~\cite[sections `6.6.' and `6.11.']{Rust-Reference}.

Since Rust supports conditional compilation~\cite[section `The cfg\_attr attribute']{Rust-Reference}
the set of items exposed by a crate and its dependencies can be changed when compiling it.

\subsection{The Repository and Manifest Traits}\label{sec:traits}

The core of Vinculum are the `Repository' and `Manifest' traits which
represent the repository and manifest file described in \Cref{sec:algorithm}.
They are intended to be implemented by repository implementations provided by the
users of Vinculum and define the methods used by the types defined in the
library to interact with them.

By making users implement the traits for their repositories they are allowed to
define their own repository interfaces designed for their implementation choices.
Extending the Repository and Manifest traits with methods not used by the fossil
collection and deletion steps to provide users with a common interface was considered
during development with the reasons for its abandonment explained in \Cref{sec:changes}.

One important difference between the methods defined by the traits and the approach
taken by Duplicacy is the way the list of clients existing in the repository is
acquired when validating \nameref{para:policy3}.
Since Duplicacy seems to acquire it from the list of existing manifest files
it is unable to take clients into account which have not created any manifest
files yet, allowing fossils referenced by the first manifest file of each client
to be erroneously deleted~\cite[topic `Prune command details']{Duplicacy-Forum}.
To prevent this the repository trait defines a method to explicitly request the list
of currently existing clients, expecting it to be kept up to date according to
\Cref{thm:adding-clients} and \Cref{thm:removing-clients}.

\subsection{The FossilCollection Struct}

The `FossilCollection' struct represents a fossil collection created by a fossil
collection step.
It stores the data required by a fossil deletion step and provides methods to
perform it.

Since the fossil collection is usually persisted (for example by being stored
in the file system) while the client waits until the fossil deletion step can be
performed its has to be able to be serialized and deserialized.
A popular way of implementing this in the Rust ecosystem consists of defining
traits for types which can be (de)serialized and types representing possible
ways of performing the (de)serialization, for example by choosing the format
of the serialized data.
These traits are provided by the `Serde'~\cite{Serde} framework and implemented
for the FossilCollection struct should the `serde' feature be activated when
compiling the crate.

Making users opt into using Serde allows them to remove the dependency on it
should the required functionality be implemented in another way.

\subsection{The FossilCollectionBuilder Struct}

To perform a fossil collection step a client has to instantiate the
`FossilCollectionBuilder' struct which provides the necessary methods to
create a fossil collection.
Its name comes from the `Builder' design pattern which encapsulates the creation
of a complex object, in this case the FossilCollection struct~\cite{GoF}.

The fossil collection step requires choosing which manifest files to
delete~\cite[Algorithm 1]{Duplicacy}, which depends on the backup retention
policy used by the users of Vinculum.
To prevent all manifest files from being downloaded twice by the user evaluating its backup
retention policy and the fossil collection step requiring downloading all manifest
files~\cite[Algorithm 1]{Duplicacy} the task of downloading them is delegated to the user.
This way the user can perform the necessary operations to determine which manifest files
should be deleted and pass the resulting information to the FossilCollectionBuilder by
marking individual chunks as either being referenced or possible fossil candidates.

When performing the fossil collection step the FossilCollectionBuilder will turn
all fossil candidates which where not marked as being referenced into fossils.
Should the client already know which manifest files to delete the result would be
the following procedure (with all functions except `deleteManifestFiles' being
provided by FossilCollectionBuilder or the Repository or Manifest traits):

\begin{algorithm}[H]
    \caption{Example of a user performing a simple fossil collection step.}\label{algo:fossil-collection}
    \begin{algorithmic}[1]
        \State $builder \gets \Call{createBuilder}$
        \ForAll{$manifest \in \Call{existingManifestFiles}{repository}$}
            \If{$manifest \notin manifestFilesToDelete$}
                \State $chunks \gets \Call{downloadChunkReferences}{manifest}$
                \State \Call{markAsReferenced}{chunks, builder}
                \State \Call{markAsSeen}{manifest, builder}
            \EndIf
        \EndFor
        \ForAll{$manifest \in manifestFilesToDelete$}
            \State $chunks \gets \Call{downloadChunkReferences}{manifest}$
            \State \Call{markAsFossilCandidates}{chunks, builder}
        \EndFor
        \State $fossilCollection \gets \Call{collectFossils}{builder, repository}$
        \State \Call{deleteManifestFiles}{manifestFilesToDelete}
    \end{algorithmic}
\end{algorithm}

In addition to the methods used to mark chunks as referenced or possible fossil
candidates the FossilCollectionBuilder also provides methods to perform the operations
described in \Cref{sec:unreferenced-chunks} and \Cref{sec:abandoned-fossils}.

\subsection{The RepositoryExt Trait}

Using the FossilCollectionBuilder can include a lot of boilerplate code should
the user only use simple backup retention policies such as \Cref{algo:fossil-collection}.
To reduce it the `RepositoryExt' trait provides methods implementing shortcuts
to using the FossilCollectionBuilder and is automatically implemented for types
implementing the Repository trait.

\subsection{The PipelinedFossilCollectionBuilder Struct}

When executing the Lock-Free Deduplication algorithm for an extended period of
time it is very likely that the fossil collection and deletion steps will be
performed periodically to reclaim space for new backups being created.
Since the client performing them has to alternate between executing a fossil
collection and deletion step it can only remove fossils on every second invocation.
Performing a fossil collection step immediately after completing a fossil deletion
step allows the client to delete fossils on every invocation should \nameref{para:policy3}
not cause the fossil deletion step to be delayed which is depicted in \Cref{fig:pipelining}.

Since performing the fossil deletion and collection steps back to back causes
all manifest files existing in the repository to be downloaded twice~\cite[Algorithm 1 and 2]{Duplicacy}
the manifest files should be downloaded once and shared between them.
This is possible by using the `PipelinedFossilCollectionBuilder' struct in place
of the FossilCollectionBuilder.

The difference between them is that the PipelinedFossilCollectionBuilder also
performs the fossil deletion step of an existing fossil collection but does not
discard the downloaded manifest file information.
After performing the fossil deletion step it will use this information to produce
and instance of the FossilCollectionBuilder struct which can be used to perform
a fossil collection step without downloading additional data from the repository.

\subsection{Iterator and Error Types}

Besides the aforementioned types there exist also a number of helper types
which represent errors or iterators~\cite{GoF} used by the other types.

While the iterator types are often very simple they increase encapsulation by
controlling which details of the iterators provided by the internally used data
structures are exposed to the user.

The error types on the other hand allow for a more fine-grained error reporting
and make it possible for multiple methods consuming a type to return its ownership
to the caller should they encounter errors, allowing the operation to be retried.

\section{Parallelism}\label{sec:parallelism}

There are multiple steps in the Lock-Free Deduplication algorithm which have no
ordering requirement between them, such as renaming individual chunks or fossils
or downloading individual manifest files.
To allow clients to better utilize the resources of the repository Vinculum
can be instructed to perform them in parallel.
Since the way parallelism is achieved varies depending on the repository implementations
supplied by the users the `std::future::Future'~\cite{Rust-Docs} trait of the Rust
Standard Library is used to provide a uniform interface to them.

For example, an implementation communicating with a remote machine over the network
may use asynchronous I/O facilities such as the `poll'~\cite{Posix} function of
POSIX conforming systems while other implementations may queue work on a
thread pool to access the local file system or perform CPU-intensive tasks.

While this increases the complexity of using Vinculum it allows reusing
implementations of these approaches such as event loops and thread pools from
existing libraries such as `Tokio'~\cite{Tokio}.

\section{Changes and Problems during Development}\label{sec:changes}

When starting development the first prototype was implemented without using the \\
`std::future::Future'~\cite{Rust-Docs} trait of the Rust Standard Library.
While this made using it very simple it also meant that a thread pool would be
required should parallel execution be desired.

Since a custom thread pool would make it difficult for users of Vinculum to
integrate it with their approaches to parallel execution or other libraries it
was decided to use the approach described in \Cref{sec:parallelism}.

Another difference to the current implementation was the Repository and Manifest
traits providing additional methods, such as to create chunks and manifest files.
The intent was to provide a unified interface on which future abstractions such
as chunk creation, compression and encryption could be implemented.
While creating the implementation used in \Cref{ch:evaluation} it was discovered
that designing an interface to be used by all the possible solutions to these
problems was harder than anticipated.
To prevent the design of the traits from limiting adoption it was decided to
use the approach described in \Cref{sec:traits}.
